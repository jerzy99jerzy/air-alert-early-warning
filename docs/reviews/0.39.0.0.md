# Review 0.39.0.0: what the alarm counts measure, and what a reader is told

Version: 1.0 / 2026-08-23

The reading that produced this release started from an operator's observation
rather than from a gate: Kharkiv showed **1** alert over seven days, and that
looked wrong. It was not wrong about the rule the code implements. It was wrong
about everything the number is read as, and the reading found the same error in
four documents across two repositories.

Everything below is `[measured]` by running the shipped functions against
constructed event logs. Nothing here was concluded by reading the code and
reasoning about what it would do; that method is what let the defect stand.

## 1. The finding

`trailing_counts` opens an episode when an oblast goes from no raion under
alert to at least one, and closes it only when the last active raion is
affirmatively cleared. Both halves are deliberate and both are defensible in
isolation. Together they mean the count rises only when an oblast has gone
*completely quiet* and become loud again.

Eight Kharkiv raions, seven-day window:

| Constructed log | `alerts_count` |
| --- | --- |
| 20 oblast-wide alerts, each cleanly cleared | 20 |
| The same 20, one raion's all-clear never arriving | **1** |
| The same 20, that all-clear arriving as `UNKNOWN` | **1** |
| 40 single-raion alerts, staggered to overlap | **1** |
| The same 40, spaced so they never overlap | 40 |

**The same forty alerts count as 40 or as 1 depending only on whether they
overlap**, and neither branch is an error condition: overlap is the normal
state of an oblast under sustained attack, and a declaration closed by silence
rather than by an affirmative all-clear is the normal behaviour of the source.

The number is therefore lowest exactly where attack is heaviest.

## 2. How far it had travelled

The consumer shades its map from this field. Measured: an oblast struck sixty
times with overlapping raion alerts renders in bucket 1; an oblast with six
clean, discrete, fully cleared episodes renders in bucket 2. **The map drew the
quieter oblast darker.** That is F76's failure in a new direction - the shading
stopped measuring how finely an oblast is subdivided and started measuring how
often it fell completely silent.

Beside the number, four documents told a reader it meant something else:

- `mavo/report.py`, twice: *the count errs in the direction that does not
  understate*. True of the alert state, false of the count.
- `docs/WEBAPP.md`: `recent_7d[]` *counts declarations*, which is precisely the
  number F76 was logged for removing.
- the consumer's `week_caption`: *deklaracje alarmu* / *alert declarations*.
- the consumer's `contract_fields` justification: the same phrase again.

The last three trace to the first. One wrong word in a contract row became
three wrong sentences downstream, in two repositories, in front of readers -
and the fourth was surfaced by the consumer's own gate printing its
justification during a run, not by anybody searching for it.

## 3. Why the apparatus did not catch it

`trailing_counts`' docstring already contained the answer, written a dozen
releases earlier about F76:

> The regression that should have caught it used one raion, so the mutation had
> nothing to bite.

**The lesson was written down and the fixtures were not changed.** A
single-raion fixture cannot express overlap, so no mutation of this fold could
ever have gone red on it. The mutation register was full and green over a
blind spot it could not reach.

The second mechanism is that prose was reviewed as prose. No check compares a
rationale against the behaviour it argues for, and no check joins a consumer
caption to the producer contract row it paraphrases. Both sentences read
plausibly and both were wrong in the direction that flatters the number.

## 4. What shipped

`alert_seconds` and `still_under_alert` on `RecentOblast` and `RecentArea`, in
`state.json` and `feed.json`, bounded by `tools/contract_check.py` against
their own window.

Three properties decided the shape and each is pinned by a regression:

- **A union, not a sum.** Two raions under alert for the same hour give the
  oblast one hour. Summing would reproduce F76's arithmetic in a new field.
- **Clipped at both edges.** A stretch running for thirty days reports seven,
  so a share of the window cannot exceed one and a shading scale needs no
  bucket edges chosen by eye.
- **Clamped at `as_of`.** T40 measured the source's clock disagreeing with ours
  in both directions; no arithmetic may publish minutes that had not happened
  when the picture was composed.

`alerts_count` stays. "How many separate flare-ups" is a real question; it is
simply not the question the column was being read as.

## 5. Two things worth keeping from the method

**A repair that changes more than the defect is a second defect.** The first
candidate for F113 - reading only the first physical line of a status blob -
moved six entries where four were wrong, breaking T40 and T50. It was refused
on a before-and-after measurement of all seventy entries rather than on taste,
and the shipped repair moves exactly four.

**A test that cannot fail is worse than no test.** The first version of the
future-timestamp regression passed against both the clamped and the unclamped
fold, because the `max(0.0, ...)` guard absorbed a lone future declaration. It
was rewritten as a closed pair only after the named mutation stayed green. That
is the same fixture-blindness this release is otherwise about, caught inside
the fix for it.

## 6. What this release does not do

The consumer still shades by `alerts_count`. It cannot do otherwise until this
release reaches production and `alert_seconds` is actually in the payload the
site reads. The shading change, and the retirement of `INTENSITY_EDGES`, are
consumer work with a producer dependency and are scheduled behind it.

`INTENSITY_EDGES` also carries no derivation - no comment, no distribution, no
date - which is the one unsourced constant in a codebase where every other
threshold states where it came from. It was chosen against a distribution this
defect deflated.
