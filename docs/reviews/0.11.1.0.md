# Pre-push review, 0.11.1.0

The second review of this repository conducted from outside it: the 0.11.0.0
tree was read adversarially, with the running package available, by a reader
with no stake in what it already claimed. Three defects raised and repaired, one
raised and deliberately left in place because repairing it is a sprint rather
than a review, and four findings recorded as owner decisions rather than
touched.

The method that produced all three repaired defects was the same one, and it is
worth naming: **each layer was correct against its own contract and the defect
lived in the seam between two.** Reading a module against its docstring finds
nothing here, because the docstrings are accurate. Composing two guarantees and
asking what the composition promises found three in an afternoon.

## Findings repaired in this release

**F61. A timestamp that parses cleanly became an outage one layer up.**
`_parse_timestamp` accepted anything `fromisoformat` accepts, and that includes
`2026-09-01T21:00:00`: valid ISO, no offset, a naive datetime. `poll()` built an
event around it and honoured its never-raise contract; the store then refused
that event at `append` with `NaiveTimestamp` (F52). Malformed content became an
outage, one layer above the contract written to prevent exactly that. Harness
A9 covered the timestamp that does not parse and asserted `poll` returns; the
timestamp that parses into the wrong shape took a different branch and nothing
asserted the composition.

Disposition: a naive datetime is malformed at the parser and takes the unparsed
path, counted and reported.
`tests/test_telegram.py::test_f61_a_naive_content_timestamp_never_becomes_an_event`
asserts poll-to-append rather than either layer alone.

**F62. The transport would read the filesystem when handed the wrong string.**
`UrllibTransport.fetch` passed its URL straight to `urlopen`, which also speaks
`file://`. Every URL in the package is a constant, so nothing hostile could
reach it, and a latent local-file-read is only cheap to remove while it is
latent. The module's stated scope, "the one seam between this package and the
internet", is what kept every test inside that framing; nobody asked what it
does with a string that is not the internet.

Disposition: non-http(s) schemes refuse as `SourceUnavailable`, preserving the
raises-one-thing contract. `tests/test_transport.py::test_f62_a_non_http_scheme_is_refused`.

**F63. A duplicated tag in the map resolved by file order.** `AreaTable.from_csv`
wrote rows into a dict keyed by tag, so a tag appearing twice would resolve to
whichever row came later. The map has no duplicates today; the defect is that a
hand edit or a bad merge of a register update would be absorbed rather than
reported, and the map is the one artifact area resolution trusts. Same class as
F59, one layer earlier in the pipeline.

Disposition: `DuplicateTag` at load, before any resolution can happen.
`tests/test_areas.py::test_f63_a_duplicate_tag_in_the_map_is_refused`.

## Finding raised, not repaired here

**The border predicates cannot fire on real input.** The rules test
`event.area_id in BORDER_OBLASTS`. Since sprint 7, `classify` emits a KATOTTG
register code for a raion or hromada while `BORDER_OBLASTS` holds coarse oblast
slugs, so on any live event that membership test is false by construction. It is
dormant rather than active, because the rules run only over fixture nights,
where the two vocabularies coincide - which is also why 173 tests agreed with
it.

Not repaired in this release deliberately. It is a schema change touching the
event, the store and the rules, it needs a decision about which vocabulary is
canonical, and a review that quietly performs a sprint is a review nobody can
audit. Raised as T38 with an acceptance criterion, for the sprint that connects
the rules to live events.

**A rule that cannot fire is worse than a rule that fires wrongly**, and that is
the part worth carrying out of this finding. Silence is the correct output on
almost every night, so a permanently silent predicate is indistinguishable from
a working one by observation alone. Nothing in this repository's measurement
apparatus would have surfaced it; a reader had to compose two modules by hand.

## Findings recorded and not touched

Each of these is a measurement or an owner decision, not a repair, and changing
any of them inside a review would have altered numbers the project has already
published.

**The rules layer imports `Night` and `EAST_TO_WEST` from
`mavo/sources/fixture.py`.** The decision layer is typed against the synthetic
generator. It works, and it means the fixture cannot be deleted or replaced
without touching the rules. `Night` belongs in `schema.py`; moving it is a
refactor that touches the architecture pins.

**R2's westward test is endpoint-only.** `positions[-1] > positions[0]` fires on
a sequence whose last motion is eastward, as long as the last area sits west of
the first: kyiv, lviv, rivne fires. Whether that is the intended reading is a
question about the rule, and changing the predicate changes the measured gate
results the repository publishes. To be decided against the corpus, not inside a
review.

**`content_hash` joins its fields with `|`.** A theoretical collision only, and
changing the separator changes the identity of every stored row. D-013 makes
that survivable by rebuilding from the raw corpus, which is exactly why it
should happen in a release that intends it.

**The coverage pin is environment-dependent.** `STATUS.json` pinned 96.9 and a
clean 0.11.0.0 run under Python 3.12.3 measured 96.76. The pin was not wrong
when it was written; it is not reproducible across interpreters, and a
measurement block that moves with the reader's toolchain should say which
toolchain measured it.

## What this review did not do

It did not read the parser against the corpus. Every claim here is about code
composition, and the question of whether area resolution is *correct* on real
messages is what `tools/consistency_check.py` measured at 99.997% internal
agreement, which is not the same claim.

It did not exercise the network path. `UrllibTransport` is tested against an
injected response object; that a live channel behaves as the tests assume
remains untested and untestable from here, as the module has always said.

It did not review `tools/` for correctness, only for lint and type coverage.
Half the measured numbers in `STATUS.json` are produced there, and the review
that reads those tools against their own output has not happened.

## Structural changes made alongside the fixes

**The gate now audits its own instruments.** `make lint` covered `mavo` and
`tests` while `tools/harness_mutation.py` is itself part of `verify`. Ruff and
mypy now run over `tools` as well; three long lines and one union-attr fell out
and are fixed.

**Five tools carried their own copy of the snapshot-name regex, two their own
copy of the tag grammar and the western-oblast list.** That is the F36 drift
class waiting to happen, one character at a time. `mavo/backfill.py` exports
`SNAPSHOT_NAME` beside the writer that defines the grammar; the tools import
`TAG` and `WESTERN_OBLASTS` from `mavo/areas.py`.

**`EventStore.append` names its columns** instead of depending on schema order,
and `replay` iterates the cursor instead of materializing the log one line after
promising an iterator.

## Push readiness

Green: `make verify` OK, 173 tests, coverage 96.78% under Python 3.12.3 against a
floor of 95, 11 of
12 attacks mutation-verified with the twelfth printed as unverified, docs-audit
pins hold at 0.11.1.0, manual-audit clean. Verified again in the target
environment under Python 3.14 with mypy 2.3.0, where `tools/` passed `strict` on
its first run.

Outstanding and deliberately unresolved here: T38 (the vocabulary split above),
T37 (the pipeline discards areas it was told about), T32 (border distance), T7
and the threat-model residual re-probe, both of which are MVP Audience C
criteria that remain unmet while the repository is public.
