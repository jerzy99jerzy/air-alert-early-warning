# Review of 0.35.0.0

Version: 1.0 / 2026-08-20
Baseline: `main` at 0.34.0.0, gate green. Three gate checks, one register entry,
one corrected procedure and one documentation sweep. **No runtime path
changes**, and nothing ships to the host.

---

## What the three checks have in common

Each of them sits beside a check that was already there and already green.

`check_defect_count_is_pinned` counts entries in `docs/METHODOLOGY.md` and
compares that count against `STATUS.json` and against the README badge. Three
artefacts, one number, all agreeing, for every release since 0.6.0.0 — and
F108 was cited in `CHANGELOG.md` for two days without an entry, because a count
cannot notice an absence it was never told about. The new check reads the
changelog and asks the register. Same subject, opposite direction, and neither
substitutes for the other.

`check_badges_match_the_pins` reads the shields.io URL. The alt text beside it
drifted to 410 while the badge said 427 and stayed that way for a release. The
URL was audited and the words were not, and the words are the only version of
the figure a reader with images disabled receives.

Nothing at all measured precision. 288 figures in this repository carry two or
more decimals, in a repository whose argument is that unmeasured things must
not look measured.

**The generalisation, which is the finding rather than the fix:** a check's
perimeter is not its subject. Three checks were about defects, badges and
figures; their perimeters were a count, a URL and nothing. This is F108's own
lesson — the gate perimeter is `git ls-files` and the release perimeter was
larger — arriving a third time in a different costume.

---

## Why `lint-precision` counts rather than judges

`0.076` and `7.84` are the same shape. One is fourteen failed polls in
eighteen thousand, where the third decimal *is* the finding; the other is a
week-long window quoted to fourteen minutes, where the second decimal changes
nothing anybody does. No pattern separates them, so a checker that tried would
be wrong in both directions and would then have to be argued with at every
release.

It counts per document against a ceiling, and the ceiling is exact in both
directions. Above it, a figure has appeared that nobody classified. **Below
it**, a document was cleaned and the debt was not written down, and a debt that
quietly shrinks is one nobody can report on. The limitation is stated in the
module: a count cannot tell one figure from another, so a swap passes. It
measures direction, which is what a ratchet is for, and it is the same trade
`fail_under` already makes on coverage.

The Polish variant is applied only to `*-PL.md`. A comma means one thing in
`96,61` and another in `38,521`, and which one is a property of the document's
language rather than of the string. Two fractional digits only, so a thousands
group cannot be misread; a Polish figure with three decimals is missed, and
that is a hole named here rather than found later.

## The ceilings were seeded from the wrong scan

The first pass over the tree used a pattern that also matched fragments of
version strings, and reported `docs/METHODOLOGY.md` at 212 where it holds 81.
The number reached a planning document before it was caught.

It was caught by the tool measuring the tree rather than by anybody rereading
the scan. **Same class as F102 and F104**, and the fourth instance this week:
a conclusion drawn from whichever output was open rather than from the artefact
the conclusion was about.

---

## The procedure that could not be run

After F108 the release order was written apply → add → verify → manifest. That
order **fails at `verify` whenever a release adds a file**, because
`manifest-completeness` is inside `verify` and a newly tracked file is
precisely what it refuses. Measured twice in one session while shipping
0.34.0.0.

A corrected procedure that had never been executed was carried across a
session boundary as though it were tested. The repair is in
`docs/DEPLOYMENT.md`, with a table saying what each step prevents rather than
only what it does.

---

## What this release does not do

It does not sweep the 288 figures. It records them, freezes the number, and
makes the next one visible; the sweep is the documentation sprint and it is
ordered after the host readings, because two of that sprint's items are
repaired *from* a deploy rather than before one.

It does not write entries for F14, F17, F18, F28 or F29. Those are named in a
frozen list. The releases that cited them are dated and the defects were real,
and reconstructing what they said from the number alone would put an invented
record in the file whose whole value is that it holds none.
