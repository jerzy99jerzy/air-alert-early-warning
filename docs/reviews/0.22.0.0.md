# Review, 0.22.0.0

Carried out on 2026-08-11, before the push, against the release that closed
F23 in the product two sprints after closing it in the code. D-021 asks for
this document on a major release; the release earned it for a reason the rule
did not anticipate, so the review is structured around that.

**The release began as a request to update one README paragraph.** It became a
minor-version bump with a deleted module-level table, a rewritten live path and
three rewritten test fixtures. That is worth stating plainly rather than
presenting the outcome as if it were the plan: the paragraph was stale because
the product it described had been wrong for two sprints, and nothing between
the paragraph and the code was checking.

## The finding, and what makes it different from the ones before it

F90 is not a parsing error or an arithmetic error. It is an **assertion that
certified the absence of the defect it was written to catch**. The two pins
read:

    assert matched == 0, "area table now matches; update this pin and close F23"
    assert classified == 0, "classifier now matches; update this pin and close F23"

Both were deliberate, both were good practice, and both called the untabled
code path. When sprint 7 landed the register map, these tests were the
mechanism that was supposed to notice. They did not notice, and their message
told every subsequent reader that they would have.

The README, the limitations list and the licence disclaimer all cited the pin.
So the defect had three independent-looking confirmations, all sourced from one
assertion measuring the wrong call shape.

**The last row is the one to sit with.** The two numbers that make the 0
impossible were already in `STATUS.json`, printed beside it, for three
releases. Nothing compared them because nothing was asked to. This is the third
member of a family this session already has two of: F81's two corpus counts,
F89's false reconciliation of them, and now a third contradiction sitting in
one file. The pattern is not "numbers go stale"; it is **numbers that contradict
each other are not compared unless something compares them.**

## The fixture finding, which may outlast F90

Repairing the wiring turned seven tests red. Every one was red because its
fixture was written in oblast prose - a message shape the channel does not
emit. `PAGE`, the A12 attack page and the F50 pairing fixture all encoded the
sprint 6 implementation's assumptions about its input.

This is the third instance in one session, after F85's cutoff fixture and F82's
sample. Three is enough to stop calling it an accident. **Test data chosen to
match the implementation is the dominant failure mode in this repository**,
ahead of anything in the parsing or the arithmetic, and every one of the three
was invisible until something unrelated forced the fixture to be read.

No mechanism is proposed here, deliberately. A lint that refuses fixtures
without hashtags would be a rule aimed at this instance rather than at the
class, and the repository has enough rules whose reader is the future. The
honest output of this review is the count and the name.

## What this release does not claim

- **No correctness rate.** 20 of 20 and 15 of 20 are measurements of
  *mechanism*: the parser reaches the table and the table answers. Whether the
  answers are right is T36, drawn and fingerprinted and not yet scored.
- **Twenty messages is not a sample.** They are twenty messages from
  twenty-six minutes of one afternoon in sprint 4, all eastern. They are a
  regression fixture that happens to be real, and the Wilson bound on twenty
  clean rows is 16%.
- **Nothing about the live path under load.** `probe` now reads a CSV per
  construction. On the one-shot `collect` path that is invisible; S9's
  unattended run is where it would show, and it has not been measured.

## Second pass, after the operator asked where the review had overreached

Everything above was written before that question. Four claims in it did not
survive it, and three of them had already been pushed.

**F91, and the review's own worked example.** The F85 repair was described here
and in the 0.21.5.0 changelog as one that can only raise `recent_7d` counts.
The operator ran the pre-F85 and post-F85 trees side by side on his own
machine, printing `mavo.report.__file__` from each, and the count went 2 to 1.
The claim came from reasoning through one boundary case and generalising to a
direction. Notably, the first attempt to check it *from inside this review*
also failed, and failed silently: the probe script was run from `/tmp`, so
`sys.path[0]` was the script's directory rather than the tree under test, and
both runs imported the same installed package. The verification the operator
ran is the one that holds, because it printed the module path.

**F92, provenance.** The F89 entry, whose subject is an inference sitting in a
measurement's position, contained an inference sitting in a measurement's
position. It said the count of unparseable posts was "measured 2026-08-11",
and no such run was possible: `data/raw` is excluded from every package.

**F93, the sprint numbers.** The status paragraph was rewritten to agree with
`STATUS.json` without reading what `shipped_sprints` means. It means a test
file exists. The paragraph then said "three sprints from beta" where four
remain, and a gate check was added that enforces the misleading sentence.

**Withdrawn without a number: the post-id item.** This review logged a defect
saying 321,498 posts should read as a post id rather than a count, on the
reasoning that Telegram ids include deletions. The corpus measurement points
the other way: 61,041 ids span exactly 61,041 posts, so across 17% of the
sequence there is no gap at all. The entry was removed before release, the
original sentence restored, and the genuine open question - whether the
sequence starts at 1 - stated with the one request that would settle it. A
defect entry written from a mechanism the tree's own data contradicts is worse
than no entry, because it spends the log's credibility.

**What the four have in common.** Every one is a claim the review generated
rather than measured, and every one was phrased with the confidence of the
measured claims around it. The measured findings in this release - 20 of 20, 15
of 20, the `probe` wiring - were all checked by running something. The four
above were checked by thinking about them. Nothing in the document distinguished
the two kinds, which is the failure the provenance labels exist to prevent and
which this review did not apply to itself.

## Decision recorded

**D-022. A default argument may not select a superseded implementation.** Where
an implementation is replaced, the old one is deleted in the same release, and
any caller that has not been updated fails loudly rather than silently getting
the old behaviour. Reopen condition: a case where the old implementation must
remain reachable for a stated migration period, in which case it is reachable
under a name that says so, never under a `None` default.
