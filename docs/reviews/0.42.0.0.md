# Review 0.42.0.0: a cursor that could not survive a process, and the note that hid it

Version: 1.0 / 2026-08-29

One defect closed that had been running in production since deployment, one
found while closing it, and one decision that had been open as a preference.
**The closed one was recorded `done` at tier 3 in sprint 5**, which is the
finding underneath the finding: this repository's backlog is better at
recording what was built than at recording what production reaches.

Everything labelled `[measured]` was produced by executing code in this
repository. No figure here is about the host, because this release has not
reached it and neither has the one before it.

## 1. `skipped` had never been a measurement on the machine that matters

`TelegramChannelSource._window` compares the current page's lowest post id
against the source object's `_last_id`. That is correct and it has been correct
since 0.4.0.0. `mavo-collect.service` is a `oneshot` under a 30 s timer, so
every poll on `vm-mavo` builds a fresh source, `_last_id` is `None`, and the
count is `unknown`. **No two polls have ever met in one process on that host.**

The acceptance T18 was closed against - "consecutive polls compare post ids and
report the skipped count" - is true of the class and false of the deployment.
F123 recorded this at 0.39.1.0 and deferred the repair, correctly, because the
cursor had nowhere to live until D-036 decided where the collector's record
goes.

**What it guards is not housekeeping.** F27: the page serves roughly the last
twenty messages, and during a mass alert the channel emits more than that in a
short period. A skipped message leaves no trace and no error code. That is the
one condition under which this entire product matters, and the only instrument
against it has been reporting `unknown` since 2026-08-11.

The repair is the store. `feed_attempts` gains `first_id` and `last_id`;
`mavo collect` reads `newest_page_id` before the fetch and seeds the source.
`[measured]`, two `main()` invocations against one store:

```
poll 1, page 100..102:  skipped=unknown  (no earlier page bound)
poll 2, page 108..109:  skipped=5
```

**The cursor is `MAX(last_id)`, not the newest row's.** Two regressions hold
that, and the second is the one worth reading: a page that comes back short
must not move the bound backwards, because a retreating cursor re-counts a
window it has already reported and does it in the shape of a measurement. The
first holds that a refusal between two reads does not lose the window, which
reading the most recent row would have done - NULL bounds on the refusal, and
`unknown` forever after.

## 2. The note that made the defect readable as a caveat

Three ways to reach the unmeasurable branch, one sentence for all three:

| State | What it means | Old note |
| --- | --- | --- |
| no `--store` | nothing could have kept a baseline | "a single poll has no baseline" |
| store, no bound yet | first poll, resolves itself | "a single poll has no baseline" |
| store, bound present, page has no ids | **restructured or hostile page** | "a single poll has no baseline" |

**F126**, and it is F44's class one more time: a diagnostic whose outcomes do
not separate its hypotheses. The third row is the one worth waking up for and
it was indistinguishable from the first two. Worse, the wording asserted an
architectural property - *a single poll* has no baseline - so a reader met it
as a permanent fact about the command rather than as a state, which is how it
survived F123 being logged against the same branch.

Three branches now, and the third quotes what it has: `the baseline is post 301
and this page carried no post ids at all`.

## 3. One rewrite that was not a defect, checked rather than claimed

`_window` set its cursor with `max(last, self._last_id or last)`. The `or`
reads as a guard against a falsy cursor. It is not one - and it is also not a
bug:

| `_last_id` | `or` result | `max(last, …)` | Correct value |
| --- | --- | --- | --- |
| `None` | `last` | `last` | `last` |
| `0` | `last` | `last` | `max(last, 0)` = `last` |
| `5`, `last`=3 | `5` | `5` | `5` |

Every input already produced the right answer. It is written out because the
field is now seeded from outside the process, where a reader has more reason to
ask what a zero would do, and it is recorded in the register **as a non-defect**
with the table above. A release that quietly takes a defect number for a
tidy-up is padding the register, and the register's only value is that it does
not.

This is worth stating because the first draft of this change carried the
sentence "silently accepts a page that would move the bound backwards (F126)",
which is false. The arithmetic was done after the sentence was written.

## 4. The workflow, and why the duplicate run stays

`on: [push, pull_request]` runs the matrix on every branch and every tag.
Measured on `v0.39.0.0`: two runs, 38 s and 40 s, one commit. `mavo-site`
refuses this under D-S57; this repository did not, and nothing recorded the
difference as a choice.

**D-037 names the triggers and keeps the tag run.** The argument for keeping it
is narrow and worth stating narrowly: `actions/checkout` resolves the ref it is
given, so a tag run answers *does the tree this tag points at pass*. The
release procedure's rule is to tag on the full commit hash and never on `HEAD`,
and a tag on the wrong commit is exactly what that rule prevents and what
nothing else here can catch - the local gate runs before the tag exists, and
`make manifest` on the push reads the commit.

**What a green tag run does not mean**, and the decision says so: in the
ordinary case it re-reads identical bytes and is not independent evidence about
the code. It is a check on the pointer.

The cost that is real: branch pushes other than `main` stop building. Single
maintainer, work on `main`, pull requests still run.

## 5. What is now available and was not asked for

`tools/attempts.py` reports unseen messages across the window, because the
bounds are in the table. It is reported *beside* unobserved seconds and not
added to it: a stretch with no attempt in it is time we were not looking, and
this is traffic that moved while we were. Pairs whose bounds are missing on
either side - every row written before this release - are counted and printed,
so a total over half the pairs cannot read as a total over all of them.

This was not in T66's acceptance and T66 is closed. It is here because the data
arrived and the alternative was a table nobody reads.

## 6. What this release does not establish

**Nothing about the host.** Three releases now sit between `main` and
`vm-mavo`, two of them changing `mavo/` and the store schema. F123 is still
running in production and will be until the deploy lands. Every figure in
sections 1 and 2 is from a container.

**Not a sprint.** Same as 0.41.0.0 and for the same reason: the open tier-1
items are counsel, conversations, a population that has not appeared, and
measurements on a machine. This is repairs and an instrument.

**The contract field is still not published.** D-034 waits on a host reading,
which 0.41.0.0 said and this release does not overturn.

## 7. What the next release owes, unchanged and now larger

1. **Deploy.** Count the `[STORE-MIGRATED]` lines: two from 0.41.0.0, three
   from 0.40.0.0, and never again after the first poll.
2. **Read the first two polls.** The first reports `skipped=unknown` with the
   "no earlier page bound" wording; the second carries a number. A large number
   on the first would mean the cursor was seeded from something older than the
   deploy, which cannot happen and is cheap to rule out once.
3. **A week, then `tools/attempts.py`**, then `docs/CHANNEL.md` 8a.
4. **Then** D-034's field.

Steps 2 and 3 are new since the last review and they are the reason the order
has not moved: each is the input to the next, and taking step 4 first publishes
a number nobody has looked at.
