# Review, 0.26.0.0

Carried out on 2026-08-13, against the release that gave the refusal a
duration. D-021 asks for this on a major release.

## What this release is, and what it is not

It is one line of output changed and four regressions holding it there. It is
not an explanation of the 11% unreachable rate, and the entry in T39 says so
in those words. **The distinction matters because a release that appears to
address a measured failure, and does not, is worse than no release: it closes
the item in a reader's mind.**

## The thing worth recording

Eleven refusals were logged over one night on the production host before
anybody noticed that `[UNREACHABLE] <urlopen error timed out>` answers no
question. The line named a failure and gave nothing that could separate its
causes: a stall that hit the ten-second ceiling, a rejection that bounced
immediately and a name-resolution failure all printed the same way.

**That is F44 applied to diagnostics rather than to scheduling.** F44's rule
is that a probe whose outcomes do not separate its hypotheses is not a probe.
This project has since written that sentence into three task entries and a
defect entry, and still shipped a log line that violates it, ran it for a
night, and read the output eleven times.

The general lesson is not "add timing to log lines". It is that **the rule was
being applied to tests and not to output**, and output is where a running
system does its reporting. Every refusal path in this package deserves the
same question: if this fires, what can a reader rule out?

## What the tests hold, and one that was rewritten

The elapsed figure is asserted against **two different durations**, so a build
that printed a constant fails. The first version of the command-level check
asserted on a string inside `cli.py`, which would have passed against a build
that carried the substring in a comment and printed nothing; it runs the
command against a refusing transport instead. That correction was made before
the release rather than after, which is the only reason it is a footnote here
rather than an entry in the defect log.

## What is still open, and it is the same thing as yesterday

- **T39.** The unreachable rate has a mechanism proposed and no measurement
  choosing between it and the alternatives. What changed is that one night of
  journal can now do the choosing.
- **T54.** The staleness machine has still never been watched crossing. At a
  measured one poll in eight, a reader will get there before the operator
  does, and the site has been publicly reachable since 2026-08-12.

Both need a host and wall-clock time rather than work in this repository,
which is why they have outlasted several releases that could be written
without leaving the editor. That pattern is worth naming: **the tasks that
survive longest here are the ones that cannot be closed by typing.**
