# Review of 0.36.0.0

Version: 1.0 / 2026-08-20
Baseline: `main` at 0.35.0.0, gate green. One defect entry, one change to the
only file in the package that touches the network, nine regressions, two tasks.
**This is the first release in this session that changes what runs in
production**, and it is the reason the deploy is no longer optional.

---

## The finding, and why it is worse than a wrong number

`docs/DEPLOYMENT.md` pinned the collector's poll failure rate at 0.076%. It is
between 9.7% and 10.6%.

The part worth carrying forward is not the size of the error. It is that
**0.33.0.2 corrected the README towards it.** That release was a deliberate
audit of every claim in one document against the tree, it found seven stale
claims, and it recorded that six of the seven understated the project. One of
its repairs replaced "roughly one poll in eight fails" — an approximation of
one in ten — with a pin that was wrong by a factor of a hundred and thirty.

The audit was reading documents against documents. `README.md` disagreed with
`docs/DEPLOYMENT.md`, and the newer, more precise, more official-looking figure
won. Nothing in that process could have caught this, because the machine was
never asked. **Internal consistency is not accuracy, and a repository whose
gate enforces the first can arrive at a wrong number by agreeing with itself.**

---

## How the pin was built

Numerator: 14, fetches over 15 seconds in the seven days after F98 landed.
Denominator: "roughly 18,350 polls", which is within two per cent of the count
of *successful collections in the whole journal*, a nine-day span. Two windows,
one quotient.

It survived because it was plausible in both directions. F98 had just made
every timeout land at ten seconds, so counting fetches over fifteen seconds
returned a small number honestly; and the denominator was a real count of real
lines. Only the ratio was meaningless.

**A refusal does not print `Finished mavo-collect`.** It prints
`Failed to start` with `status=3`. Every count of "polls" taken from `Finished`
lines in this project has been a count of successes wearing the name of
attempts, and that is what made the S9 window's arithmetic look short: 7,076
successes plus 774 refusals is 7,850 attempts over 259,200 seconds, a 33.0 s
cadence against a measured median of 33.0 s.

## What was excluded, by measurement rather than by argument

The failure is a SYN that leaves and is not answered: `time_connect` zero, no
bytes, the whole budget spent.

| Explanation | How it was excluded |
| --- | --- |
| DNS | 40 probes with the address pinned and resolution skipped refused at the same rate as 40 with it |
| The absent IPv4 route | 20 consecutive fetches all chose the AAAA record; the A record was never tried |
| Path MTU black hole | it completes the handshake and stalls on transfer; these never reach the handshake |

**Which side drops the packets is `[unknown]`** and T70 holds it at tier 3,
because the repair works whichever the answer is.

Two hypotheses of mine died here and both died on data. IPv4 fallback was
stated as the leading candidate and 20 probes killed it. MTU was offered as
its replacement and the phase timings killed it in the same run.

## The repair, and the size of the evidence under it

`CONNECT_BUDGET_S = 2.0`: every successful connect measured took 23 to 55 ms,
so two seconds is thirty-six times the slowest success. It cannot cut off a
connection that was going to work, and it stops paying the whole fetch budget
for silence.

One retry, **made only when the connection was never established**. A request
that arrived may have been received and acted on, so repeating it is a decision
about the far side rather than about our own timeout. That every fetch here is
a `GET` is not the reason this is safe: a `GET` that arrived is still a `GET`
that arrived.

**The evidence is seven observations and the entry says seven.** 7 of 7 retries
connected, giving a one-sided 95% lower bound of 65% on retry success and a
repaired rate between 1.1% and 3.7% `[inference]`. T69 carries the measurement
that settles it, and its acceptance is written so that failure reopens F109
rather than closing T69.

## Two things done to the suite, both named

**An F98 regression was preserved rather than adjusted.** The test asserting
that a deadline is spent across addresses instead of repeated would now read
`[2.0, 2.0]` where it reads `[10.0]`. Changing the expected numbers would have
retired an F98 invariant to make an F109 feature pass. It names its connect
budget explicitly instead, so it still proves what it was written to prove.

**A clock stub held exactly two readings**, which encoded a belief about how
many times the code under test calls `time.monotonic`. F109 reads it a third
time to decide whether a retry still fits the deadline. Unbounded after the
first reading now.

And one thing observed and left alone:
`test_the_elapsed_figure_distinguishes_a_fast_failure_from_a_slow_one` patches
`urllib.request.urlopen`, which stopped being the seam at 0.28.1.0. It passes
because the real resolver fails on `example.invalid` — it tests the right thing
for the wrong reason, and reaches the network to do it. Repairing it is a
different change from this one.

## The precision lint contradicted itself within one release of being written

Its module comment said ceilings "may only fall". Its error message said
"round the new one, or raise the ceiling with the reason". Both shipped at
0.35.0.0 and this release is the first to need the distinction: F109's entry
quotes `0.076` deliberately, because a figure wrong by two orders of magnitude
is evidence and rounding it would soften the record.

The comment now matches the message. One ceiling rose with its reason, one
fell because the section around it was rewritten and its figures rounded, and
both movements are recorded in the table itself.
