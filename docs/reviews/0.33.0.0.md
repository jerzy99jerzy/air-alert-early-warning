# Review of 0.33.0.0

Version: 1.0 / 2026-08-19
Baseline: `main` at 0.32.10.0, gate green. This release adds one fold, two
contract fields and eleven mutants. **It changes no measurement and ships
nothing to the host**; the S9 unattended window closes 2026-08-20 11:02:06 UTC
and a deploy resets it.

---

## The question this release closes

`docs/WEBAPP.md` carried an open contract question: should `recent_7d` entries
gain `border_km_lower` and `border_km_upper`, and if so, should an oblast's
interval span all its areas or only the areas that were actually active in the
counted episodes? The producer-side recommendation was the second, with the
cost named: the same oblast would report a different interval week to week
without the geography moving.

**Both answers are wrong, and for a reason the question could not see.** They
differ on which set to take the extent over; they agree on producing an extent.
An extent over a set of raion measurements is not a measurement of the oblast.
Its lower bound comes from one raion and its upper from another, so the
interval describes no single place, and publishing it under the same field
names as the per-area interval - which describes exactly one - puts two
different quantities under one name in one payload. A consumer writing one
reader for both, which is what shared field names invite, would print them in
adjacent sentences and a reader would have no way to see the difference.

The question is therefore withdrawn rather than answered, and the two blocks
are separated by granularity instead:

| Block | File | Granularity | Carries a distance |
| --- | --- | --- | --- |
| `recent_7d[]` | `state.json` | oblast | **no** |
| `nearest_7d` | `state.json` | raion | yes, one place |
| `recent_7d_areas[]` | `feed.json` | raion | yes, per place |

## Why the producer has to do this at all

The consumer's `geometry.json` carries 25 oblast outlines and nothing finer
[reported, from the consumer, 2026-08-19]. A distance at raion granularity is
therefore not something the consumer could compute differently; it is something
the consumer has no geometry to compute at all. This is not a disagreement
between two methods, it is one side holding the only inputs.

The same fact retires an earlier comparison in this project's own notes. A
raion interval was once measured against an oblast polygon and the 156 km
difference was read as a discrepancy between two methods of measuring one
thing. It was the size of Donetsk oblast.

## Placement, measured rather than argued

`state.json` on `vm-mavo` is **13,150 bytes** and is polled every thirty
seconds. `feed.json` is 116,406 bytes and is fetched when a reader opens the
history panel [both measured, 2026-08-19].

The per-area block is 10.2 KiB for the western areas alone and 35.5 KiB for
every area the map knows [measured against `tag_map.csv` and `border_km.csv`].
In the polled file that is a growth of 78% to 270%. The reduction the page's
headline actually needs is one object at 241 bytes.

So the bulk travels in the file that is fetched on demand and the scalar
travels in the file that is polled. Both come from one composition, so the
headline cannot name an area the history block does not list, and the gate
asserts that rather than trusting it.

## What the fold restates, and why restating was necessary

`trailing_areas` keys on the area. `trailing_counts` keys on the oblast.
Nothing the first does follows from what was proved about the second, so three
invariants are written again rather than inherited:

- **UNKNOWN does not close an episode.** A source that stops naming a raion has
  not said its alert ended.
- **An episode overlapping the window's left edge counts once, wherever it
  opened (F85).** The whole log is replayed; a cutoff applied as a filter would
  age out the opening transition of a long alert and render the most
  persistently attacked area as the quietest.
- **An unresolvable area is dropped, never folded into a neighbour.**

`last_active_at` for an episode already running at the cutoff is the opening
time, which predates the window. Reporting the cutoff instead would invent a
transition that never happened.

## F76, asserted instead of described

Summing `episodes` across an oblast's areas does not give that oblast's
`alerts_count`, and the difference is the whole of F76: one western episode
lights every raion at once, so the sum measures how finely the oblast is
subdivided rather than how often it was attacked. The field is named `episodes`
so that a consumer reaching for `alerts_count` gets a `KeyError` rather than a
plausible number, and there is now a regression that fails if the two counts
ever agree on a fixture built to separate them.

## Mutants

Eleven, all killed. Six against the fold: UNKNOWN closing an episode, the F85
cutoff applied as a filter, unknown distance sorting first, the count renamed
to `alerts_count`, the block moved into the polled file, a distance added to
the oblast block. Five against the contract check: `nearest_7d` dropped, the
block copied into `state.json`, the order reversed, the reduction taken from
the far end, the count renamed.

**One survived the first attempt.** The ordering test built a table in which no
area had a distance, so there was nothing for the unknown to sort against and
the assertion held whichever way the comparison went. Rewritten against a table
where one area has a distance and one does not, which is the only shape in
which the two orderings are distinguishable. Sixth logged instance of a fixture
whose shape made the thing under test unable to fail. The count is the finding,
not the fix.

## What this release does not do

It does not deploy. It does not touch the collector, the store, or any
measurement. `docs/CHANNEL.md` section 8a is still empty of the T40 row,
because the latency distribution measured on 2026-08-19 has an unresolved term
in it: the share of the tail attributable to unreachable polls rather than to
the channel. A row that assigned our blindness to the source would be worse
than no row.
