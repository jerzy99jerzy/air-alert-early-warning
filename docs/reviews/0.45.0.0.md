# Review 0.45.0.0: what the switchover looked like from the reader's side

Version: 1.0 / 2026-08-30

0.44.0.0 shipped and deployed the same afternoon, and this release is what the
first evening of running it found. Both defects are the same shape: a
vocabulary belonging to somebody else, translated into this project's own, with
the destination deciding the answer instead of the source. `[measured]` means
executed in this repository's container or read from `vm-mavo` during or after
the switchover.

## 1. The gate could not have caught either of these, and that is the finding

Both defects are internally consistent. `AIR → MISSILE` type-checks, has tests
asserting it, and offers the mutation runner nothing to flip; the prose
candidate that swallows `територіальна` is exactly what the documented
algorithm says it should be. Every instrument this repository owns compares the
tree against itself, and neither defect is a disagreement inside the tree.

**What caught them.** The missile mapping was caught by a reader looking at the
map legend and asking whether the icons were right. The prose defect was caught
by taking the nine `unresolved` names off a production run and probing them
against the table one by one, rather than accepting the count. Both are the
same method: compare the output against the world, not against the repository.

The honest conclusion is that a gate step is not being added for either, and
the reason is not laziness. A check that the kind mapping is "correct" would
have to encode what the API means by `AIR`, which is the very thing that was
got wrong; it would restate the assumption in a second place and go green.
Where a check *is* possible - the four prose forms now resolve, the five
uncovered names still do not - it exists, and it is a regression test rather
than a truth-checker.

## 2. The kind mapping, and the cost it uncovered

`AIR` is now UNKNOWN. The reasoning is D-042 and is not repeated. What belongs
in a review is what the repair revealed rather than what it fixed: **the
switchover cost this project the classification of the means of attack**, and
D-040 did not name that cost when it was written this morning. Two of three
kind-dependent rules now have no input at all.

This is worth stating plainly because the failure mode is arithmetic rather
than visible. `r3_border_missile` was, for four hours, a rule that fired on
every air alert in a border oblast; any evaluation run touching that window
measures the mapping, not the sky. The drone rule now cannot fire, and a rule
that cannot fire reports zero exactly like a rule that fires correctly and
finds nothing.

## 3. The frozen episodes, and the condition that was missing from the first draft

The first version of D-041 in this session had two conditions: the area is in
the table, and the API did not list it. It was wrong, and the measurement that
showed it is worth recording. Donetsk oblast resolves perfectly well from prose
and alerts as a *state*; the eight frozen Donetsk raions are separate area ids
that the API will never mention while it names their parent. Two conditions
would have closed all eight and written a quiet front line into the store.

The third condition - no containing area may be alerting - exists because of
that reading. It was found by measuring rather than by reasoning, and the
reasoning that preceded it was confidently wrong about the cause while
accidentally right about the conclusion.

## 4. Gate

`verify: OK` in the container on 3.12.3: 583 tests, mutation runner intact,
`ruff` and `mypy --strict` clean, all lints and audits green. Coverage and test
count are pinned in STATUS.json from this run and not restated here.

**CI on 3.11 is unmeasured for this release as of writing**, for the same
billing reason that stopped the consumer's run: this is stated so that a later
reader does not mistake a green local gate for a green matrix.

## 5. Errors by the agent, on equal footing

**Class 3, twice, both about Donetsk.** First: concluding that the eight frozen
Donetsk raions were unresolvable by name, from the shape of the unresolved list
rather than from probing the table - `Донецька область` resolves and always
did. The conclusion "do not close them" survived; the stated reason was false,
which is worse than being wrong outright, because a false reason that reaches
the right answer does not get corrected. Second: proposing "the four-token
limit" as the cause of the prose failures, from the two longest names, when
three-token names failed identically and the limit was never the constraint.

Both were caught by measurement inside the same session. Neither would have
been caught by the gate.
