# Pre-push review, 0.5.0.0

Sprint 6, part one. One acquisition capability and two defects, both in how this
repository checks things rather than in what it built.

## Findings

**F44. Two sprints of schedule built on a probe that could not fail.** The claim
that the corpus could only be collected forward in time was a property of one
command generalised to the channel without ever being tested against it. When it
was finally tested, the test asked for posts before id 1000000 against a channel
whose newest post was 321498, which returns the newest page whether the parameter
works or is ignored.

Disposition: corrected in one request once the cursor was inside the real range.
The general remediation is in CONTRIBUTING.md: before running a probe, state what
it would print if the thing being tested were false, and if that is the same as
success, it is not a probe.

The honest accounting of the cost: nothing built on the wrong belief is wasted,
because window-gap detection is needed for continuous collection either way. What
was lost is ordering. Sprint 5 was scoped around a constraint that did not exist,
and the recommendation to start a cron immediately was urgency manufactured by an
unchecked assumption.

**F45. The red-verification probe imported the code it was verifying.** The
sprint 6 suite passed against a scratch copy of 0.4.0.0 that did not contain
`backfill.py`, because the editable install resolved the package to the working
tree. Survived ninety seconds; recorded because it silently defeats the standing
regression rule for every sprint that adds a module, which is most of them.

Disposition: `pip uninstall` before the probe, documented as part of the rule.
Re-run after uninstalling: red, on import. Noted in CONTRIBUTING.md that an
ImportError is weaker evidence than a failed assertion, and where the previous
state can be shimmed, it should be.

**`mavo backfill`.** Writes raw pages, named by id range, resumable, paced. Five
named stop conditions and a contiguity check with its own exit code. It parses
nothing beyond post ids, which is the load-bearing constraint: the corpus exists
because the pattern table scores 0 of 20, and a corpus filtered through that
table would be evidence about the table rather than about the channel.

**D-012.** The design/holdout boundary declared before any content is read. This
matters more now than it did last week: with twenty messages there was nothing to
overfit to, and with hundreds of thousands there is. The boundary is the newest
20% by post id, and the reason for newest rather than oldest is that the redesign
must survive the channel as it writes today.

## What was deliberately not done

No message content was read. The corpus has not been fetched, only the tool to
fetch it. The pattern table still scores 0 of 20 and its pins still hold. T21,
measuring the tolerated request rate, is deliberately ahead of the large run: the
default delay is a guess made conservative on purpose, and it is labelled a guess
rather than presented as a rate limit.

## The honest reading of this sprint

Two of the last three sprints found their most important defect in the
verification machinery rather than in the product: the harness that measured less
than it claimed (F38 to F40), and now a probe that could not fail and a
red-verification that verified nothing. The pattern is not carelessness in
writing checks. It is that checks are written to pass, and a check nobody has
seen fail is an assertion about the author's intent rather than about the tree.

## Measured at review time

`make verify` green: 143 tests passing, 11 of them harness attacks, coverage
96.46% against a floor of 95. Ten of ten mutations killed. Channel measurements
on 2026-08-09: page size exactly 20, newest post id 321498, backwards paging
confirmed with a cursor inside the real range.
