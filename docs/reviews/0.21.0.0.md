# Review, 0.21.0.0

Carried out on 2026-08-10, before the push, against the release that rebuilt
`docs/BRIEF.md` and added `docs/BRIEF-PL.md`. The first review the new rule
(D-021) demanded rather than the author remembering to write.

The release is documentation only. There is therefore one question worth
asking of it, and it is not about prose: **does the brief state anything the
tree does not support?** A document written for a reader who cannot check the
code is the easiest place in the repository to be wrong without consequence.

Two claims in the brief were not in the table above because they are not
figures, and both were defective:

- **A specific incident**, with a date, a voivodeship and a duration, opening
  the section on where the project came from. It appears nowhere else in the
  repository and carried no provenance label, in a document whose own text
  promises that every number carries one. It came from the working session
  rather than from the tree and was written in the register of settled fact.
  Removed at 0.21.2.0 rather than sourced, because the argument does not
  need it.

Both were found by the operator asking where a claim came from, not by this
review, which had checked the eleven things that are easy to check and called
that a verification of the document.

**What that says about the review.** A review that enumerates the checkable
and reports a clean result is a review of the checkable, and its summary line
must say so. This one said "no figure in the brief is unsupported", which was
true and irrelevant: the two defects were a fabricated fact and an overstated
adjective, and neither is a figure.

## The finding

**The previous brief described the tree as it stood fifteen releases earlier.**
Its status section said the component that reads the meaning of a message does
not work, citing 0 of 20. That was true at 0.11.x and was repaired at 0.12.0.0,
when the reader moved onto the channel's own hashtags. It stayed in the
document because nothing reads prose.

This is F73's family again and it is worth counting how many times that family
has now appeared: the README's tables, the review record, four documents
describing a review-per-release practice, and now the brief's status section.
Five instances, all the same shape, all in documents rather than code. The
common cause is not carelessness. It is that this repository's gate is
excellent at pins and blind to sentences, and every one of these lived in a
sentence.

**Disposition:** corrected in this release. No new check. A check that reads
prose for staleness is not a thing this project knows how to build, and
pretending otherwise by adding a weak heuristic would be worse than the honest
statement that documents are checked by people re-reading them.

## Findings raised and not repaired

**The brief has no reader in the gate at all.** Its figures were verified by
hand for this review and nothing will notice when the next one drifts. The
figures that appear in both the brief and `STATUS.json` could in principle be
pinned the way the README's tables now are. Not done here: the brief phrases
numbers in prose ("about 20% of alerts", "roughly 57% of days") and pinning
rounded prose against exact pins would produce a check that fails on
rewording. Recorded as a real gap rather than solved badly.

**The Polish version is the original and the English one is downstream.** Every
other document in this repository is English-only, so a second language is a
second thing to keep in step, and nothing checks that the two briefs still say
the same thing. The risk is concrete: a correction applied to one and not the
other. Accepted deliberately, because the readers this document exists for are
Polish and a translated-feeling document reads as a document about somebody
else's problem.

## What was not reviewed

The prose itself, for whether it lands with its audience. That needs a reader
from the audience, which is drill D12 in the site's test plan and has no
equivalent here. The author is not able to review his own document for
comprehensibility and neither is a language model that helped write it.
