# Review, 0.24.0.0

Carried out on 2026-08-11, before the push, against the release that gave the
product a path from the live channel into its own store. D-021 asks for this
on a major release.

**This is the first defect in this repository found by a machine other than the
author's laptop**, and that is the only thing about it worth a review.

## What actually happened

Two virtual machines were provisioned in `europe-central2`. The collector
reached the channel over IPv6 with no IPv4 address at all, the suite passed 310
tests on Debian, `mavo collect` returned `messages=20 parsed=19 unparsed=1`
against real traffic, the site rendered `state=blind` correctly, and the push
channel refused a malformed file and accepted a valid one.

Then `mavo-report.service` entered a restart loop. `sqlite3.OperationalError:
unable to open database file`. The immediate cause was mine - the runbook
created `/var/lib/mavo/events` as a directory when the store wants a file path.
Fixing that would have produced a report writer rendering `blind` for ever,
because **nothing in the product fills a store from the channel**.

## Why the gate could not have caught this

The defect is the **absence of a caller**. `TelegramChannelSource` parses and is
tested. `EventStore` records and is tested. `probe` counts and is tested.
Nothing joined the first to the second, and no test of any of the three could
express that, because each is correct in isolation and the missing thing is an
edge rather than a fault.

This is a genuinely different class from the rest of this log. F90 was a
tripwire wired to the wrong path; F94 was a resource whose lifetime was the
caller's attention span; F95 was a task whose justification expired. All three
were findable by reading. **This one was findable only by running the system in
the shape it is meant to run in**, and the repository has never done that.

## The uncomfortable arithmetic

`docs/MVP.md` gives S9 an exit criterion of 72 hours unattended with every cycle
accounted for. T25 argued for a real host on the grounds that a sleeping laptop
writes a record whose holes look like quiet nights. Both were right for reasons
narrower than the truth: **the laptop could not have run shadow mode at all**,
and nobody noticed because nobody tried.

Seven releases shipped today. Ninety-seven defects are logged. The store had no
producer for the entire time, and the number of tests grew by three today
without any of them being the one that would have mattered.

The honest reading is not that the process failed. It is that **a process built
around reading code finds defects in code, and this one was not in the code.**

## What was decided rather than implemented

**Both streams or neither.** `--store` writes alerts and declarations together.
Storing only the alerts would have been half a line shorter and would have
produced a store whose kind coverage read zero for reasons no measurement could
attribute. The regression asserts both.

**Exit code 7 for a store that cannot be written.** Consistent with
`--save-raw`'s code 4 and the report command's 5 and 6. A wrapper reading stdout
must not be able to mistake a lost write for an empty sky.

**`probe` kept rather than replaced.** It has callers and tests; `poll_once`
delegates. Two functions polling the channel is how the two would eventually
disagree, so there is one and a thin reading of it.

## What this release does not claim

- **The command is still one-shot.** Running it every two minutes is a systemd
  timer, which is a deployment decision, not a feature. `skipped` remains
  `unknown` on every poll because a fresh source has no baseline for post ids -
  the sprint-6 note in that branch is still true and still unaddressed.
- **Nothing has run for 72 hours.** The path exists; the measurement does not.
- **Latency end-to-end is still unmeasured.** T40 needs the resident collector
  this release does not provide.

## Recorded for the next reader

The runbook that produced this deployment is outside the repository, and it
contained the directory-versus-file error that surfaced the defect. That error
was cheap and the finding was not. **If the deployment documents come into the
repository later, they come with their own gate**, because a runbook that is
wrong in a way that produces a correct outcome by accident is worse than one
that fails loudly.
