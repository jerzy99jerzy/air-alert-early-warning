# Review of 0.36.0.1

Version: 1.0 / 2026-08-21
Baseline: `main` at 0.36.0.0, deployed to `vm-mavo` and **failing 10.9% of
polls with a traceback**. This is a hotfix and it repairs a defect this
release train introduced.

---

## What happened, in the order it happened

0.36.0.0 capped each connect attempt at two seconds. Before it, the first
attempt spent the entire ten-second deadline, so `connect_within` always broke
out of its loop on an exhausted budget after one address. The cap left eight
seconds behind, and the loop reached the second entry for the first time in
eight releases.

The second entry was not a second host. `socket.getaddrinfo(host, port)`
without a `type` returns `SOCK_STREAM`, `SOCK_DGRAM` and `SOCK_RAW` for each
family. `connect()` on a datagram socket returns immediately - there is no
handshake to fail - so it looked like a successful connection, and TLS then
refused it from inside the standard library with `NotImplementedError`.

That is a `RuntimeError`. Not the retry's tuple, not `fetch`'s tuple, not
`_cmd_collect`'s `except SourceUnavailable`. It walked out of the process.

**168 polls in 14 hours died this way**, exiting `1/FAILURE` where the
contract says `3`, and writing no `[UNREACHABLE]` line at all.

---

## The reading that followed, which is the worse half

With the refusal line gone, a count of refusals over that window returned
zero. This session read that zero as a network that had gone quiet, wrote that
T69 had met its threshold, and closed F109 - **twenty-four hours after logging
F109, which is the defect of dividing by a number that measures something else
than it names.**

The rate had not moved. 168 of 1,539 is 10.9%, against 9.9% the day before.

A count of a token measures the token. It stands in for the event only while
the code that writes it is on the path, and nothing checked that. The
correction is in T69: before dividing by anything, confirm the line exists at
all.

---

## Why the regressions could not have caught it

The F109 suite handed `connect_within` two addresses and made both
`SOCK_STREAM`. That is what its author believed `getaddrinfo` returns, and the
belief was written into the fixture rather than checked against the interface.
The tests passed on a model of the resolver that was wrong in exactly the way
the production code was wrong.

This is the recurring class in this repository, and it appeared here in a test
written the same day as the code it was defending. The repair is two tests: a
resolver that returns a datagram address deliberately, and one that asserts
against the **real** `getaddrinfo` that the six-entry premise still holds, so
the regression cannot decay into testing its own stub.

---

## Three repairs where one would have been the same bet

`resolve_stream` filters to `SOCK_STREAM`. That is the defect at its source
and on its own it would be enough for the production path.

`_attempt_one` refuses a non-stream candidate. The resolver is an injectable
seam; a repair that lives only in the default protects the caller that uses
the default and nothing else.

`fetch` maps **any** exception to `SourceUnavailable`, with the type named in
the message so widening the net does not also hide what it caught. The old
tuple was a guess about what `http.client` plus `ssl` can raise. It survives
as `RETRYABLE`, deciding only what is worth a second attempt - where narrow is
correct, because an exception nobody predicted is not evidence that trying
again would go better.

---

## What this release does not do

It does not measure anything. F109 is **reopened**, T69's first window is
**void**, and both need a fresh 24 hours after this lands. The estimate that
one retry takes 10% to between 1.1% and 3.7% is still an inference from seven
observations, and the mechanism has now been in production for fourteen hours
without executing once.
